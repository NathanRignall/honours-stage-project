Zephyr is an open-source real-time operating system written in C \autocite{zephyrZephyrprojectrtosZephyr2024}. VxWorks is a commercially available real-time operating system \autocite{hambardeSurveyRealTime2014}. These are both OS's that are specifically designed for real time applications. While they both support the Raspberry Pi 4, neither publicly support the Compute Module 4 and Zephyr lacks support for ethernet IC on the Pi 4.

Alternatively the PREEMPT\_RT patch is available for mainline Linux, that aims to minimise the amount of kernel code that is non-preemptible  \autocite{linuxfoundationRealtimeDocumentationStart}. The patch prefers deterministic behaviour over throughout and makes a number of changes to the kernel including replacing kernel locks with rtmutexes. However some resource management functions (memory management) have indeterminate maximum latencies. This patch results in a soft real-time operating system as the kernel is not designed to guarantee deadlines \autocite{maddenChallengesUsingLinux2019}.

Although Linux with the PREEMPT\_RT patch was not strictly suitable for real-time applications it was chosen as the operating system for developing the software infrastructure. This was because Linux has a wide support for software libraries, build environments and has many user guides for development.

Linux also supports containerization through cgroups and namespaces, which could be useful for creating the isolated processing environments \autocite{huynhKubernetesStoryLinux2023}. In case of a real deployment, the software should use a more suitable operating system such as VxWorks. Both OS's are Unix-like so should porting the software should be fairly trivial.

\subsection{Hypervisors}

To reap the benefits of dynamic updates it is preferred that the hypervisor is independent of the operating system. This is so that different operating systems can be upgraded during operation, using the hypervisor functionality to run new virtual machines. 

The KVM hypervisor is implemented on top of the Linux kernel, so is discarded from the search. Also, in a true real-time system it is unusual to use Linux. Rather a more preferable real-time OS such as Zephyr might be used. Using KVM as the hypervisor would constrain the system to Linux's real-time behaviour.

\textcite{ayresVirtualisationMeansDynamic2019} completed a short study into the different available virtualisation technologies for embedded safety critical systems. Notable hypervisors from the study include VxWorks, Xen, Sel 4 which all have public support for the Raspberry Pi 4.

Xen was selected as the hypervisor for evaluation because of its independence from Linux and open-source nature. It also had extensive documentation available compiling Xen for a Raspberry Pi 4 target device.

\subsection{Build Process}

All software images for the development cards were created using the Yocto Project build environment because of it's support for both Linux and Xen. Although some images for Linux were initially created manually, this process was exceptionally slow and an inefficient use of time. Yocto is an open source project that uses various layers to build an image using scripts \autocite{linuxfoundationYoctoProject2024}.

Xen version - 4.18

Linux kernel version - 6.1.6

\begin{itemize}
    \item \verb|poky| - Base Yocto distribution (4.3.3) \autocite{yoctoPokyPokyBuild2024}
    \item \verb|meta-openembedded| - Embedded drivers \autocite{openembeddedOpenembeddedMetaopenembedded2024}
    \item \verb|meta-raspberrypi| - Raspberry Pi focused drivers \autocite{yoctoMetaraspberrypiHardwareSpecific}
    \item \verb|meta-virtualization| - Virtualisation applications (Xen) \autocite{yoctoMetavirtualizationLayerEnabling}
\end{itemize}


A custom layer (\verb|meta-cm4-uboot-fix|) was required in order to fix issues with the uBoot bootloader. As the CM4 has onboard flash, the numbering of the eMMC boot drives was slightly different from the Pi 4. Hence a patch was required to modify uBoot's source. Another layer (\verb|meta-rpi4-kernel|) was used to pin a specific kernel version. This ensured all images generated used a consistent kernel version.
