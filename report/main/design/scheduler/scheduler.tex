To implement an event-based cyclic scheduler, the scheduler must be able to send signals between processes without significant jitter and latency. This is because the signals effectively send execution requests for each component and if there are significant delays, the component will not execute when desired. The level of latency and jitter that is acceptable can be estimated by calculating a worst-case execution time for a control loop in a particular application.

There are several different methods that can be used to send signals between processes in a Linux system. Shared memory, sockets and signalling were all investigated as they could be easily migrated onto a non-linux POSIX compatible system if required. \subsubsection*{Test Program Design}

% past tense
Each evaluation used a parent-child arrangement of processes, whereby a parent process spawned a child process. These processes were both be given the highest real-time scheduler priority and pinned to two separate cores that were isolated from the operating system. This was to ensure that no other application could interfere with the tests.

The parent process ran at a controlled frequency of 100Hz for 3,000 iterations, each iteration requested the child process to execute. At each execution, the time requested $t_0$ and actual execution time $t_1$ were recorded, shown in \autoref{fig:parentChildExecuteDelay}. These were later evaluated where $\Delta{}t$ is calculated.

\subsection{Shared Memory}

% present tense
On a Unix system each process has its own virtual memory space, so no process can normally access the memory of another process. This is to ensure proper isolation between processes. Shared memory can be used to allow multiple processes to access the same memory segment, though synchronisation methods such as mutexes must be used to ensure data and program integrity. \autocite{kentstateuniversitySharedMemory}

To allocate \verb|shmget()| returns an identifier \verb|shm_id| that can later be used to access the memory segment. \autocite{ShmgetLinuxManual2024}. To add the memory segment to the current processes the \verb|shmat()| function is used, when provided with the \verb|shm_id| \autocite{ShmopLinuxManual2024}. Conditional variables, a synchronisation method, can then be waited on using \verb|pthread_cond_wait| \autocite{Pthread_cond_timedwait3pLinux}.

% past tense
To access the shared memory functionality of Linux in the Rust language, this test used the \verb|shared_memory| crate  \autocite{elast0nyElast0nyShared_memory2024}. The parent process created two shared memory locations and a files containing the \verb|shm_id|. Using the shared memory, event synchronisation data structures were created using the \verb|raw_sync| crate \autocite{elast0nyElast0nyRaw_syncrs2024}. These events could then be used to signal when the child process should execute \verb|send_event| and when the task had completed \verb|recv_event|. The parent then spawned the child process which indefinitely looped and waited (blocked) for an event to execute.

\subsection{Sockets} \label{sec:schedSockets}

% present tense
Unix domain sockets are a useful tool for implementing interprocess communication (IPC). They are a special type of socket that behave similarly to local network sockets but bypass the network stack for efficiency. These sockets can either be unnamed or bound to a filesystem path \autocite{UnixLinuxManual2024}. 

% past tense
The second test implemented a simple unnamed socket pair between a parent and child process. The child socket was shared with the child process using file descriptors with the \verb|command_fds| crate \autocite{googleGoogleCommandfds2024}.

To signal the child component a two byte message was sent from the parent. This contained a byte indicating run and another byte with the iteration loop and was useful in ensuring no executions were missed. The iteration loop was incremented on the parent process from 0-255, the child checked the message was exactly one increment up from the previous iteration.

\begin{figure}[ht]
    \centering
    \includegraphics[width=\textwidth]{rt-pi4-socket-times-blocking.pdf}
    \caption[Experiment latency graph for blocking sockets]
    {Experiment latency graph for blocking sockets}
    \label{fig:rtPi4SocketTimesBlocking}

Although the blocking socket test did perform reasonably well, it was on average over 50\% slower than the shared memory conditional variable implementation at $30{\mu}s$.

The was assumed to be because of how the sockets are implemented in the Linux kernel. When the child process is blocked waiting for a message, the time taken to move the process back into the unblocked state is unpredictable. This is in contrast to the conditional variables which appeared to move out of the blocked state much quicker. With further investigation into the kernel, this could be investigated but is out of the scope of the project.

\newpage

To prove this is due to the process taking time to move out of the blocked state additional tests were performed. These test used a non-blocking socket which instead busy waited on receiving data. The results of this approach are shown in \autoref{fig:rtPi4SocketTimes}.

\begin{figure}[ht]
    \centering
    \includegraphics[width=\textwidth]{rt-pi4-socket-times.pdf}
    \caption[Experiment latency graph for non-blocking sockets]
    {Experiment latency graph for non-blocking sockets}
    \label{fig:rtPi4SocketTimes}
\end{figure}

The non-blocking socket performed much better than both the blocking socket and events in shared memory with an average latency of $13{\mu}s$ ($462{\mu}s$ including overruns).

However, approximately every 100 cycles (1 second) significant latencies were introduced at over 40ms, making this solution completely unviable for a real-time system. It is assumed that these latencies are introduced periodically due to the kernel itself being moved onto the CPU. As the program is busy waiting it never enters the blocked state. Therefore it consumes 100\% of the CPU resources with no opportunity for the kernel to perform management functions.

To resolve this, the scheduler could use a combination of both the blocking and non blocking sockets. The scheduler could first wakeup a component process using a blocking socket, once on the processor the component can now busy wait for a short period of time on the non-blocking socket. Then the scheduler can send the execute command. This reduces the uncertainty of when the process will execute, but overall takes much longer to execute a component as two sequential messages are sent each cycle. An expected latency could be around $13{\mu}s + 19{\mu}s = 32{\mu}s$.

To work around this the components could be put into the busy state on alternating processing cores. Component $a$ could be put into the busy wait and executed, while component $b$ is in the blocked state. These could then be alternated. While this would improve the real-time responsiveness of the system, it would unnecessarily consume CPU resources and increase latencies.

This potential implementation is shown in \autoref{fig:socketDualComponentExecute}. The dashed red and blue lines represent when the components start and exit a busy wait state. If the goal was to ensure an exact time of execution across a number of synchronised schedulers this solution would be ideal. As this is a single scheduler, the additional compute utilization is unnecessary and simply adds additional time to a control loop.

\subsection{Signalling}

Signals can be used in Linux to notify processes of actions, they are commonly used to kill processes \autocite{SignalLinuxManual2024}. However, there are many more signals available to use, some are shown in \autoref{tbl:linuxSignalsSample}. 

\begin{table}[ht]
    \centering
    \begin{tabular}{l|ll}
        Signal  & No & Description      \\ \hline
        SIGINT  & 2  & The process was interrupted. \\
        SIGKILL & 9  & The process was explicitly killed .  \\
        SIGCONT & 18 & Used to resume processes after SIGSTOP.  \\
        SIGSTOP & 19 & Used to block process and have it's state is persevered. 
    \end{tabular}
    \caption[List of relevant Linux signals \autocite{dowlingListSignalsWhat}]
    {List of relevant Linux signals \autocite{dowlingListSignalsWhat}}
    \label{tbl:linuxSignalsSample}
\end{table}

The final scheduling method investigated was Linux process signalling. No additional Rust crates were required as \verb|libc| implements the signalling functionalities.  However, the signal-based programs were implemented slightly differently. Rather than acknowledging a response to the parent process, the child simply executed. This was because the signals tested were unidirectional, unlike the sockets and memory. This simply removes the overrun detection in the parent for the child process and should not impact the test results. To request execution the parent triggered \verb|SIGCONT|, after execution the child put itself to sleep with \verb|SIGSTOP|.

Shown in \autoref{fig:rtPi4SignalTimes} the signal-based scheduler approach resulted in a latency of $17{\mu}s$. This was the best of the different implementation methods tested.

\subsection{Evaluation}
Signals performed the best ($17{\mu}s$) out of the different techniques tested with shared memory a close second ($19{\mu}s$). Therefore signals were selected as the primary choice for implementing an event-based scheduler. This does assume that the target runtime support signals, for example a virtual machine architecture may not allow signals between environments. In this scenario a shared memory implementation should be selected.

A socket-based scheduler solution could theoretically be developed if it was the only communication medium present. However, the extra work required to make a viable solution is out of the scope of this project, given the available solutions.
