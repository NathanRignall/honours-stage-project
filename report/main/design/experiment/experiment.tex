\section{Experiments} \label{sec:experiment}

The outlined experiments shall be used to validate the correctness of the software before, during and after a software update.

\subsection{Instrumentation}

To isolate specific timings within the software infrastructure the software can be instrumented to measure the time to execute specific management functions. By recording timestamps ranging from $t_0$ to $t_4$ the execution length of each section can be calculated, including slack time. This is displayed in \autoref{fig:instManagmentSchedule}.

All experiments shall use this instrumentation to ensure that at all points during operation and software upgrade the system obeys the cyclic execution frequency. This can be calculated by summing the execution time of all functions and evaluating if it less than the cycle period. These times shall be saved to disk at the end of operation so that the instrumentation does not significantly affect the timings.

% What is success?
While this is a experimentation technique rather than case, success shall be measured against the schedule overrun metric. At no point in operation can the system exceed the defined control loop period, in any test case scenario.

\subsection{Test Harness}

To externally validate the real-time behaviour of the software infrastructure, the test harness described in section \ref{sec:testHarness} shall be used. This measures the end-to-end latency of the software infrastructure in an isolated hardware environment. The system shall follow a software upgrade as described in section \ref{sec:demoWalk}

A successful experiment will complete a software update without altering the response timings recorded on the logic analyser. The response time from signal generate to receive should be consistent during software update. This validates hardware handover (\ref{sec:hardware}) and optimal time (\ref{sec:optimal}).

\subsection{Plant Model}

To compliment the hardware test harness, another test case was created to further validate the live software update process. The goal of this test was to more closely resemble an implementation of a real-time controller.

A drone flight controller usually maintains six degrees of freedom, this can be simplified to a single degree of freedom in a virtualised environment. A new controller can then be made to solely control this axis. \autoref{fig:plantModelForcesDiagram} displays the forces arrangement of the chosen environment model, a single object of mass $m$ is falling due to gravity. A thruster can fire to produce force $t$.

To simulate the environment a plant model can be created that calculates all the forces and positions. The controller can subsequently be sent information from the plant, to calculate when the thruster should fire, using a simple PID controller. This is shown in \autoref{fig:plantControllerModelArange}.
