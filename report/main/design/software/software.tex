\subsection{Architecture}
The following designs elaborate upon the defined software infrastructure requirements, explaining how the components, messages and task lists will integrate together.

\subsubsection{Components}
Each component shall operate in its own isolated processing environment to enable proper separation between components (\ref{item:reqSIComp}). Hence, the software infrastructure must be able to start and stop these environments and keep track of them in the node.

To ensure each component implements a consistent interface for the software infrastructure to use, all components will implement a common abstract class. This class is shown in \autoref{fig:umlComponentAbstractClass}.

\begin{figure}[ht]
    \centering
    \begin{tikzpicture}
        \begin{abstractclass}[text width=10cm]{Component} {0,0}
            \operation{new() : Component}
            \operation{run(Services)}
            \operation{loadState(Vec(u8))}
            \operation{saveState() : Vec(u8)}
            \operation{resetState()}
        \end{abstractclass}
    \end{tikzpicture}
    \caption[Component abstract class]
    {Component abstract class}
    \label{fig:umlComponentAbstractClass}
\end{figure}

First \verb|new| shall execute when the component is first initialised and \verb|run| shall execute whenever specified in the cyclic schedule. The run procedure is passed \verb|services| as a parameter, this contains all the classes for the component to interface with the software infrastructure.

The state operations (\verb|loadState|, \verb|saveState|, \verb|resetState|) can be used to control the persistent state of the component. Load and save both use byte arrays as interfaces, this is so that the software infrastructure does not need to be aware of the data being stored. Hence, each component can implement their own custom functions, so transformations as described by \autocite{wahlerDisruptionfreeSoftwareUpdates2014} could theoretically be implemented.

\subsubsection{Scheduling}
To run the component at the correct times, the software infrastructure will implement a cyclic schedule (\ref{item:reqSIComp}). This schedule will use an arrangement of major and minor frames to alternate different sub-schedules. 

All major frames have the same configured deadline, this determines the main control frequency. Major frames alternate so that different components can execute at different frequencies. For example if a schedule contained three major frames, and a component was present only in one major frame, it would run x3 the frequency of the main schedule.

Within a major frame, there are several minor frames. Each minor frame contains a single component execution and a configured deadline. If a component exceeds its deadline, its execution shall be paused and resumed in the next iteration. This is to maintain soft real time guarantees.

The configuration shown in \autoref{fig:schedFrameCollection} displays an example major-minor frame schedule. The main cyclic schedule runs at 1000Hz because of the $1000\mu s$ major frame deadline. Component $a$ operates at 1000Hz as it is present in every major frame. Component $b$ and $c$ both execute at 333.3Hz as they are present in $1/3$ of the frames. The arrow at the end of the frame represents the slack time available at the end of each cycle.
    
\subsubsection{Communications}
To implement \autoref{item:reqSIMessRoute} the software infrastructure shall implement a message router within the software infrastructure. Every communication pathway will be statically defined in configurations to facilitate the dynamic software update process. When components are upgraded, their communications shall be modified in software to handover control. This design choice directly resolves the hardware handover issue with live software updates.

\autoref{fig:communicationSoftwareArchietcture} displays how a communication configuration may look with the message router. Two components are connected together with two separate routes and channels for bidirectional communication. One component is connected directly to an edge device with a single channel and another component is connected to an external message router.
