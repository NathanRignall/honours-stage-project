\subsection{Architecture} \label{sec:designArch}
The following designs elaborate upon the defined software infrastructure requirements, explaining how components, messages and task lists will integrate together to enable dynamic software updates.

% overall concepts

\subsubsection{Components}
Each component shall operate in its own isolated processing environment to enable proper separation between components (\ref{item:reqSIComp}). Hence, the software infrastructure must be able to start and stop these environments and keep track of their state.

To ensure each component has a consistent interface for the software infrastructure to use, all components will implement a common abstract class. This class is shown in \autoref{fig:umlComponentAbstractClass}, represented as a UML diagram.

\begin{figure}[ht]
    \centering
    \begin{tikzpicture}
        \begin{abstractclass}[text width=10cm]{Component} {0,0}
            \operation{new() : Component}
            \operation{run(Services)}
            \operation{loadState(Vec(u8))}
            \operation{saveState() : Vec(u8)}
            \operation{resetState()}
        \end{abstractclass}
    \end{tikzpicture}
    \caption[Component abstract class diagram]
    {Component abstract class diagram}
    \label{fig:umlComponentAbstractClass}
\end{figure}

First \verb|new| shall execute when the component is initialised and \verb|run| shall execute whenever specified in the cyclic schedule. The run procedure is passed \verb|services| as a parameter, this contains all the classes for the component to interface with the software infrastructure.

The state operations (\verb|loadState|, \verb|saveState|, \verb|resetState|) can be used to control the persistent state of the component. Load and save both use byte arrays as interfaces, this is so that the software infrastructure does not need to be aware of the data being stored. Hence, each component can implement their own custom functions to encode and decode raw data. Transformations as described by \textcite{wahlerDisruptionfreeSoftwareUpdates2014} could theoretically be implemented also.

In addition, a static function \verb|run| shall be provided by the component package, outside the abstract class. This contains the functionality to complete processing with the services/scheduler and creates the component executable.

\subsubsection{Scheduling}
To run the component at the correct times, the software infrastructure will implement a cyclic schedule (\ref{item:reqSIComp}). This schedule will use an arrangement of major and minor frames to alternate different sub-schedules. 

All major frames have the same configured deadline, this determines the main control frequency. Major frames alternate so that different components can execute at different frequencies. For example if a schedule contained four major frames, and a component was present only in one major frame, it would run $1/4$ the frequency of the main schedule.

Within a major frame, there are several minor frames. Each minor frame contains a single component execution and a configured deadline. If a component exceeds its deadline, its execution shall be paused and resumed in the next iteration. This is to maintain soft real time guarantees.

The configuration shown in \autoref{fig:schedFrameCollection} displays an example major-minor frame schedule. The main cyclic schedule runs at 1000Hz because of the $1000\mu s$ major frame deadline. Component $a$ operates at 1000Hz as it is present in every major frame. Component $b$ and $c$ both execute at 333.3Hz as they are present in $1/3$ of the frames. The arrow at the end of the frame represents the slack time available at the end of each cycle.

As the low-level runtime environment is not yet determined, the scheduler shall use an event based cyclic scheduler. This is a simple scheduler that sends 'request' along a communication medium for a component to execute. When requested, the component immediately executes.

The scheduler concepts resolves dynamic software synchronisation issues from section \ref{sec:synchronisation}. The software infrastructure has fine grain control of when components execute so even during updates, all components can be synchronised.

\subsubsection{State Synchronisation}
State synchronisation shall take state from one component (in the form of a byte array) and copy it to another component. This design solves state transformation issues highlighted in section \ref{sec:state}.

By default all components shall send their current state to the synchronisation software, which stores all states. Only when a synchronisation map is added plus activated, describing the source and destination components, will the state buffers be copied. \autoref{fig:stateSyncSoftwareArchietcture} shows an example state synchronisation between an old component ($Component$) and its new version ($Component^{\prime}$).

\subsubsection{Communications}
To implement \autoref{item:reqSIMessRoute} the software infrastructure shall implement a message router within the software infrastructure. Every communication pathway will be statically defined in configurations to facilitate the dynamic software update process. When components are upgraded, their communications shall be modified in software to handover control. Hence, this design choice directly resolves the hardware handover issue with live software updates in section \ref{sec:hardware}.

\autoref{fig:communicationSoftwareArchietcture} displays how a communication configuration may look with the message router. Two components are connected together with two separate routes and channels for bidirectional communication. One component is connected directly to an edge device with a single channel and another component is connected to an external message router.

\subsubsection{Services}
To enable components to use the communication pathways and state synchronisation, the software infrastructure provides the services package. The package shown in \autoref{fig:umlServicesPackageClass} contains the class state manager and communication manager. Additional classes could be added in the future to expand functionality.

State manager is not designed to be used directly by a developer's component implementation, but rather the component runner. Theoretically a developer could use these features if required, but the runner should handle loading and unloading state though the component's implementation of \verb|loadState| and \verb|saveState|.

The communication manager is designed to be used by application code providing the methods \verb|getMessage| and \verb|sendMessage|. Get message returns a single message for a given channel, if one is present in the buffer. Send message accepts a message to send on a given channel. 

The \verb|run| procedure should be called by the runner automatically, this takes data off the sockets and puts it in the \verb|messages| hash map.

\subsection{Management}
The concepts described in the software architecture are realised by the management program. This implements the scheduler, message router, state synchronisation utilities and an interface to configure the system.

This program runs a cyclic control loop at a configured frequency executing the various components and services in the order, scheduler, router, state synchronisation, management.

\subsubsection{Task Lists}
The software infrastructure shall be configured using task lists, with each task representing a number of actions that should be performed on the system.

Some actions may be long running and take multiple execution cycles to complete. Therefore there shall be two classes of action: blocking and non-blocking. A blocking action must complete in a single execution cycle and a non-blocking action can take multiple execution cycles to finish.

All blocking actions within a task should complete in a single execution cycle. This is so that when the system begins the next execution cycle, the configuration is always in a defined (valid) state. Blocking actions are designed to be practically instant and simply modify the in-memory configuration. This enables the real-time dynamic software updates as switching configurations should not take a significant amount of time out of the main schedule (section \ref{sec:optimal}).

The following actions configure components, the schedule, message routes and state synchronisation.

\begin{description}
    \item [Create Component] - \textit{Non-Blocking} - Load the component binary from storage and start in an isolated processing environment.
    \begin{itemize}
        \item Path - \textit{String} - Location of the new binary.
        \item Sate - \textit{Boolean} - Flag to enable state synchronisation.
    \end{itemize}
    \item [Start Component] - \textit{Blocking} - Mark the component as safe to execute.
    \item [Stop Component] - \textit{Blocking} - Mark the component as unsafe to execute.
    \item [Remove Component] - \textit{Non-Blocking} - Kill the component and remove the isolated processing environment.
    \item [Add Route] - \textit{Blocking} - Add the source and destination channels to the routing table.
    \begin{itemize}
        \item Source - \textit{Endpoint} - Address and channel
        \item Destination - \textit{Endpoint} - Address and channel
    \end{itemize}
    \item [Remove Route] - \textit{Blocking} - Remove the existing route from the table.
    \begin{itemize}
        \item Source - \textit{Endpoint} - Address and channel
        \item Destination - \textit{Endpoint} - Address and channel
    \end{itemize}
    \item [Set Schedule] - \textit{Blocking} - Update the cyclic schedule.
    \begin{itemize}
        \item Deadline - \textit{int} - Duration of all major frames, in microseconds.
        \item Major Frames - \textit{vec(Major Frame)} - List of major frames, which contain minor frames and localised deadlines.
    \end{itemize}
    \item [Add State Synchronisation] - \textit{Blocking} - Add the state synchronisation request.
    \begin{itemize}
        \item Source - \textit{Component} - Source component identifier.
        \item Target - \textit{Component} - Destination component identifier.
    \end{itemize}
    \item [Remove State Synchronisation] - \textit{Blocking} - Remove the state synchronisation request.
    \item [Wait State Synchronisation] - \textit{Non-Blocking} - Start synchronising state, wait until complete before finishing.
\end{description}



An alternative approach to task-lists could implement scheduler-like functionality into the management. Rather than providing fine-grained actions/tasks, high level actions such as 'update component' could be provided. The management could then calculate the steps required to perform such actions. This design decision was not taken to reduce the complexity of the management software and to reduce the amount of software developed. As no low-level action generation was required to take place automatically, these configurations could be hand-made by the developer. This is suitable for a small system with limited applications.

\subsubsection{Background Thread}
Some non-blocking actions cannot be simply subdivided across a number of execution cycles as they interface with external software. For example, calls to modify an operating systems schedule priorities may take a `long' period of time to return.

Therefore a background thread is required to perform these long running tasks in the background. The main management thread shall communicate with the background thread using a queue, whereby new tasks are placed in a queue and finished tasks are placed in another. To keep track of the state of the non-blocking actions in the management thread the state machine in \autoref{fig:actionStateStateMachine} is used. Every non-blocking task must implement these states.

All actions start in the \verb|Started| state and move through the states one at a time until completed. At this point the task is removed off the buffer and the next non-blocking task can start.

\begin{figure}[ht]
    \centering
    \begin{tikzpicture}
        \node[state, initial] (q1) {Started};
        \node[state, right=1cm of q1] (q2) {Running};
        \node[state, right=1cm of q2] (q3) {Stopped};
        \node[state,  right=1cm of q3] (q4) {Completed};
        
        \draw[->]  (q1) -- (q2);
        \draw[->]  (q2) -- (q3);
        \draw[->]  (q3) -- (q4);
    \end{tikzpicture}
    \caption[State machine for action state]
    {State machine for action state}
    \label{fig:actionStateStateMachine}
\end{figure}

The three non-blocking actions implement the state machine. Not all the states are required for simpler non-blocking actions.

\begin{description}
    \item [Create Component] - States
    \begin{description}
        \item [Started] - Add component to the global state without any implementation.
        \item [Running] - Send a signal to the background thread to implement the new component's processing environment and sockets by putting a background action in a buffer.
        \item [Stopped] - Check if the background thread has finished the requested task. If so put the implementation in the global state.
        \item [Completed] - Do nothing (superficial state).
    \end{description}

    \item[Remove Component] - States
    \begin{description}
        \item [Started] - Mark the component as removed in the global state.
        \item [Running] - Send a signal to the background thread to stop the component's processing environment by putting a background action in a buffer.
        \item [Stopped] - Check if the background thread has finished the requested task. If so removed implementation and component from the global state.
        \item [Completed] - Do nothing (superficial state).
    \end{description}

    \item[Wait State Sync] - States
    \begin{description}
        \item [Started] - Mark the state synchronisation as started so that state begins to transfer in the main loop.
        \item [Running] - Check if the state has finished synchronisation. If so complete the action immediately.
        \item [Stopped] - Do nothing (superficial state).
        \item [Completed] - Do nothing (superficial state).
    \end{description}
\end{description}

\subsubsection{Control}
To configure which task list is loaded the management program must accept communications from component or external devices. Adding `management' as an alternative endpoint type to component and edge is a simple way to integrate this into the message router.

Channel 1 is used to stop the middleware's operation and shutdown the system and channel 2 is to send the configuration identifiers that the manager should load.
