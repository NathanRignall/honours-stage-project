\subsubsection{Libraries}
Several software libraries were used during development; Serde, Bincode, Serde Yaml, Log, Env Logger, Uuid, Libc. Serde, a framework for serializing and deserializing data in Rust \autocite{SerdersSerde2024}, was used for all external data conversation. Bincode was used in combination with Serde to send data between components and the software infrastructure. Bincode is a simple binary encoder which allowed data to be sent binary streams \autocite{BincodeorgBincode2024}. 

For a more human-readable format Serde Yaml was used to load Yaml data into the software infrastructure. Serde Yaml implements the Serde deserialization format for the Yaml file format \autocite{tolnayDtolnaySerdeyaml2024}. Hence, all the task lists used to configure the system were written using Yaml.

To express the state of the system into the console, the Log crate was used in combination with Env Logger. Log provides a simple logging interface that other crates can implement \autocite{RustlangLog2024}. Env Logger was used to physically print the log messages to console as it can be configured using environment variables \autocite{Env_loggerSrcLib}. There were several different logging levels available; Trace, Debug, Info, Warn, Error. These different levels were useful for isolating errors in the system without using a debugger.

Uuid was used to generate unique identifiers \autocite{UuidrsUuid2024}. To interface with the Linux kernel and perform scheduling operations Libc was used \autocite{RustlangLibc2024}. The project tried to minimise the number of libraries used as in a safety critical environment all libraries must also be certified.

\subsubsection{Proessing Environment}
While the Xen could have been suitable for the project, it was not used as a method for isolating components. This was due to the added complexities it would have required synchronising virtual machines across the system, 

Instead, the scheduler was implemented on Linux using the signals approach with separate processes for each component. Theoretically, this implementation could be expanded to use Linux cgroups and namespaces to further isolate components while retaining the same scheduler implementation.

In addition to the signalling, Unix sockets were used as the communication medium for message-based communications between the software infrastructure and components. As found in section \ref{sec:schedSockets}, sockets can provide relatively low latency communication between processes in Linux.

\subsubsection{Development Issues}
After developing the majority of the software infrastructure it was found that the management function would take a long period of time to execute when loading a configuration. This was due to the slow file read and processing time required to successfully decode the Yaml configuration file. This caused issues with the program not meeting the defined frequency of 1kHz.

To fix this an additional background task was added to the management program to specifically impalement the configuration load procedure. Once the tasks were complete, the data was passed back to the main management thread for processing. While this was unplanned, the background thread load would be useful for when configurations are first downloaded over the network, rather than from disk.

\subsubsection{Summary}
The software development activities for the software infrastructure programs were a success. All software requirements were implemented to produce a real-time component system.

\subsection{Test Harness}

The intention for the test harness's signal generator and receiver software was to also use Rust. This would have allowed type sharing across both the central processing nodes and edges so that packages like \verb|bincode| could serialise messages across the network, reducing development time.

However, the Rust libraries for the W5500 did not work as expected when first tested. Many packets were dropped and the reason for this is unknown. Given more time, it is likely this problem could have been fixed. For a quick solution, the microcontroller's switched to using C/C++ in the Arduino development environment.

This allowed the built-in packages for the W5500 to be used, this fixed the packet loss problem straight away. Some modifications had to be made to support this change, as messages had to be decoded manually in C and Rust. This is displayed in \autoref{lst:decodeMessageRust} and \autoref{lst:decodeMessageArunio}.

\begin{lstlisting}[caption=Decode message (Rust), label={lst:decodeMessageRust},captionpos=b]
// first 4 bytes are channel id
let channel_id = u32::from_be_bytes([data[0], data[1], data[2], data[3]]);
// next byte is count
let count = data[4];
// rest of data is message
let data = data[5..].to_vec();
\end{lstlisting}

\begin{lstlisting}[caption=Decode message (Arduino), label={lst:decodeMessageArunio},captionpos=b]
// decode the packet
int len = Udp.read(packetBuffer, UDP_TX_PACKET_MAX_SIZE);
// first - fourth bytes are packet length
uint32_t packet_length = 0;
for (int i = 0; i < 4; i++)
{
    packet_length = (packet_length << 8) | packetBuffer[i];
}
// second - fifth bytes are channel id
channel_id = 0;
for (int i = 4; i < 8; i++)
{
    channel_id = (channel_id << 8) | packetBuffer[i];
}
// sixth byte is packet number
packet_number = packetBuffer[8];
// seventh - last bytes are data
ledState = packetBuffer[9];
updateState = packetBuffer[10];
\end{lstlisting}
