There are two main components of a Distributed Integrated Modular Avionics (DIMA) system/the processing nodes and the edges. The nodes run the main application software while the edges collect/send data from a variety of sensors/actuators. To apply dynamic software updates to a DIMA system, the focus should be within the processing nodes as that is where the majority of computing takes place.

A component-based software infrastructure solution was selected for the central processing nodes. This was to enable multiple inter-connected applications to run on a single system. There are also many mature designs, such as FASA, that implement such dynamic software updates in a component system that a new design could be based on. A message-based approach was selected to connect different components with other components and edges. This was a simple technique that enables atomic control of data flow within the system, important for firmware upgrades. This design choice is analysed in more detail in section \ref{sec:designArch}.

While little processing occurs within the edge data collectors, dynamic software updates could also be implemented here through pointer-swap update techniques. However, the focus of this project was on the main functionality of the system, hence this was left for a future implementation.

This chapter outlines the requirements for all parts of the dynamic software update solution, including the software, hardware, and test harness.

\section{Software Infrastructure}

To facilitate real-time software updates this project will develop an embedded middleware framework that shall be known as the software infrastructure. This framework should run software components which can be dynamically updated. To connect the different components together a message-based approach shall be used.

% The high-level requirements are first defined, followed by the more in-depth low-level requirement that shall be used to implement test-cases.

\subsection{Functional Requirements}

% \subsubsection{High-Level}

\begin{srsitems}
    \item The software infrastructure must provide the functionality to run software components with a cyclic schedule. \label{item:reqSIComp}
    \begin{srsitems}
        \item The software infrastructure must allow users to create/start/stop/remove software components during operation. \label{item:reqSICompStartStop}
        \item The software infrastructure must allow users to change the configured cyclic schedule during operation. \label{item:reqSICompSched}
    \end{srsitems}
    \item The software infrastructure must provide the functionality to allow components to communicate using message passing. \label{item:reqSIMess}
    \begin{srsitems}
        \item The software infrastructure must allow users to configure communications between components using routes and channels. \label{item:reqSIMessRoute}
        \item The software infrastructure must allow users to add/remove routes between software components during operation. \label{item:reqSIMessRouteChange}
    \end{srsitems}
    \item The software infrastructure must provide the functionality to save and restore state between components. \label{item:reqSIState}
    \begin{srsitems}
        \item The software infrastructure must allow users to define which software components must save state during operation. \label{item:reqSIStateSave}
        \item The software infrastructure must allow users to configure which components restore from state during operation. \label{item:reqSIStateRestore}
        \item The software infrastructure must allow users to define state transformation maps so different versions of state can be restored. \label{item:reqSIStateTransform}
    \end{srsitems}
\suspend{srsitems}

\section{Test Harness}

To accurately test the real-time behaviour of the system, an external test harness is required. While latency and jitter can be measured on target, with instrumentation, this does not independently measure the system's performance.

% The following requirements define the requirements  for a successful test harness.

% \subsubsection{High-Level}

\resume{srsitems}
    \item The test harness must measure the timed latency and jitter between sending/receiving data to/from the software infrastructure.
    \begin{srsitems} 
        \item The test harness must use independent software and hardware from the core infrastructure to verify the results.
        \item The test harness must use a hard real-time platform to measure timings, for example a microprocessor.
        \item The test harness must be paired with an analysis tool to visualize and analyse the measured data.
    \end{srsitems}

    \item An example software component, that is executed on the software infrastructure must interface with the test harness.
\end{srsitems}

\section{Development Hardware}

\begin{hrsitems}
    \item The development hardware must use dedicated development hardware and not be virtualized.
    \item The development hardware must have hardware support for ethernet networking.
    \item The development hardware must support Linux and at least one open source hypervisor.
    \item The development hardware must have full remote control, including power and data.
\end{hrsitems}
