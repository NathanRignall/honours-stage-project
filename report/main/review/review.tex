Dynamic software updating (DSU) refers to software applications which can be updated while running and without interrupting operation. \autocite{hicksDynamicSoftwareUpdating2005}

Regular firmware upgrades require systems to be taken offline for firmware change and restart, which is generally time consuming and breaks continuity. High availability systems typically use hardware redundancy to provide operational continuity throughout updates. This is at the cost of extra hardware and complexity. \autocite{raoLiveSeamlessFirmware2023}

Physical tasks performed by software are often expensive to interrupt with high down time costs. For example within power substations, a power outage for customers would be costly. Hence, software is hardley updated during an embedded systems lifetime (typically of over 30 years). There are several solutions to updating software dynamically; few of these have been adapted to real-time systems. \autocite{wahlerDynamicSoftwareUpdates2009}

This chapter evaluates the requirements for a dynamic software updates system and the challenges involved. In addition, four existing implementations of dynamic updates for real-time systems are evaluated, considering both the advantages and disadvantages of each solution.

Mlinarić completed an in-depth analysis into the challenges in dynamic software updating \autocite{mlinaricChallengesDynamicSoftware2020}. This built upon the work on previous surveys into dynamic software updating \autocite{seifzadehSurveyDynamicSoftware2013}.

\subsection{Requirements for dynamic updates}
A dynamic software system can be summarised into several requirements, regardless of the implementation. Almost every DSU approach balances between the following requirements as they are contrary to each other. \autocite{mlinaricChallengesDynamicSoftware2020}

\begin{description}
    \item [Availability/Correctness] - Performing the software update should not impact the system's availability.
    \item [Flexibility] - Any part of a running system should be updatable without downtime. This includes low level drivers and application software.
    \item [Low Overhead]- The additional infrastructure required to support software updates should impact performance as little as possible.
    \item [Simplicity] - The dynamic update system should be simple, both to reduce complexity of a system and to ease developer usage.
\end{description}

\subsection{Live \& Seamless Firmware Upgrade in Real Time Control Systems} \label{caseStudy1}
\autocite{raoLiveSeamlessFirmware2023} implements live firmware upgrades on a single microcontroller, without using any additional hardware or operating system. They describe the techniques used in both hardware and software to achieve such updates without reset (seamless).

\subsubsection*{Implementation}
The key innovations for this pap
Function and vector pointer swapping

Hardware support for vector and function pointer swapping
Compiler support for live updates and optimal switchover point
Talk about the compiler

This process uses multiple hardware features to implement the live software update processes. The first is multi-bank non volatile memory to store multiple different versions of the firmware image (usually two). Next interrupt vector swap enables hardware support for quickly swapping multiple interrupt vectors in a simple cpu cycle, rather than multiple. Ram block swap is similar and allows blocks of memory to be swapped during execution e.g. function points. Finally, a hardware upgrade flag is used to indicates whether a live upgrade is in progress.

First the controller boots into the latest firmware image on the appropriate flash bank. Upon update, the user generated request is processed in a background task and the new firmware is loaded onto the opposite flash bank. The main function the branches to the new main where the compiler generated initialisation routine is executed. This initializes any new variables and sets the hardware update register flag to indicate the update is in progress. Now the new firmware's main routine is executed, performing any variable transformations and initialisation. During this process all the previous control loop functions can still run.

\begin{figure}[ht]
    \centering
    \includegraphics[height=10cm]{raoLiveSeamlessFirmware2023_LfuFlow}
    \caption[Application live firmware upgrade flow \autocite{raoLiveSeamlessFirmware2023}]
    {Application live firmware upgrade flow \autocite{raoLiveSeamlessFirmware2023}}
    \label{fig:raoLiveSeamlessFirmware2023_LfuFlow}
\end{figure}

The controller waits for the most optimal switchover point, between control interrupts. When ready interrupts are disabled, the hardware interrupt vector table and ram blocks swap and global interrupts are re-enabled finishing the upgrade process. \ref{fig:raoLiveSeamlessFirmware2023_LfuFlow} displays this process flow during software upgrade.

\subsubsection*{Test Case}
To validate the updates they, implemented a DC-DC buck converter with a tightly regulated output voltage, typically used in server power supplies. These converters are often controlled using a digital power controller implemented on an microcontroller. A live update must complete within the  idle time between interrupts on the PSU, with less than 1us of switch time.

\subsection{Dynamic Software Updates for Real-Time Systems} \label{caseStudy2}
\autocite{wahlerDynamicSoftwareUpdates2009} defines a solution for updating component-based cyclic embedded systems, without violating real-time constraints. This implementation focused on using COTS operating systems rather than a bare-metal approach, specifically Integrity.

\subsubsection*{Implementation}
They used a custom component-based framework infrastructure on top of the operating system to execute software components, effectively an embedded middleware. Each component had its own address space with script separation and defined inputs and outputs. These components communicated using using message passing (channel buffers). A manager program (which was also an upgradable component) created and maintained the channels.
\begin{figure}[ht]
    \centering
    \includegraphics[width=8cm]{wahlerDynamicSoftwareUpdates2009_Function}
    \caption[Updating component 'History' \autocite{wahlerDynamicSoftwareUpdates2009}]
    {Updating component 'History' \autocite{wahlerDynamicSoftwareUpdates2009}}
    \label{fig:wahlerDynamicSoftwareUpdates2009_Function}
\end{figure}

How to identify points in time when an update can occur
System performs the checks at the end of every execution cycle

The updated component is sent to the target machine using OS functionality in a low priority thread and this upload is detected by the component manager. When ready, the old component is told to exit and the channels are handed back to the manager. The new component then starts its operation with the correct channels attached. Once the upgrade begins in the main thread, it must complete before the end of the execution cycle.

To enable state transfer, the component manager creates an area of shared memory that is passed to the components. Before a component terminates it writes its state to the area and adds appropriate version information. When a component is started, it reads the memory, assess if a state transformation must occur (that is present within the new components) and begins. To state transfer and execution must complete in one execution cycle.

\subsubsection*{Test Case}
The example application used to validate the dynamic software updates was an entirely virtual application. A test program known as \verb|Sensor| periodically sent the system clock value to the \verb|History| component. This component then stored a buffer of the previous 1000 values to test the state transfer.

\subsection{Disruption-free Software Updates in Automation Systems} \label{caseStudy3}
Another approach to updating software at runtime without disruption was developed by \autocite{wahlerDisruptionfreeSoftwareUpdates2014}. This uses a component based architecture developed by ABB Corporate Research (FASA), shown in \autoref{fig:wahlerDisruptionfreeSoftwareUpdates2014_FASA}.

\subsubsection*{Implementation}
FASA defines function blocks that can be aggregated together to form a component, only compute components are stateful. These function blocks are executed cyclically at a desired frequency and connected by communication channels. A background thread with low priority performs the management actions. Multiple FASA systems are synchronised over the network using precision time protocol (PTP.) While no specific real-time operating systems are mentioned, it is assumed that this component infrastructure is compatible with POSIX.

\subsection{A Model for Updating Real-Time Applications } \label{caseStudy4}
Similar to the first \hyperref[caseStudy1]{case study} \autocite{montgomeryModelUpdatingRealTime2004} performs dynamic updates using function pointer swaps. However instead of using bare metal hardware support they use features of a UNIX like operating system (RT-Match) to load and swap the new modules.

\subsubsection*{Implementation}
The first step of an upgrade is producing a replacement module. This follows the typical edit, compile, link process of developing a binary but uses a pseudo-linker instead of a traditional UNIX linker. This special linker produces loadable executable modules (significant smaller), in contrast to a traditional linker which produces a new binary of an entire application. The custom linker takes the previous binary as an input in order to calculate the differences in the symbol table.

The new module is loaded into the previous program's heap memory section, rather than the text section because the heap is dynamic. The previous application must have support for loading this module into memory. Transfer of execution occurs using pointer-function variables, whereby pointers pointing to functions in memory space are dereferenced. These pointers simply need to be updated to switch execution to a new function. This method of transfer can also be applied to upgrading a multi-threaded application.

This process relies upon the old program implementing the module load function, and using pointer-function variables.
