\subsection{Live \& Seamless Firmware Upgrade in Real Time Control Systems}
\autocite{raoLiveSeamlessFirmware2023} implements live firmware upgrades on a single microcontroller, without using any additional hardware or operating system. This paper describes the techniques used in both hardware and software to achieve such updates without reset (seamless).

\subsubsection*{Implementation}
Key innovation, 
Function and vector pointer swapping

Hardware support for vector and function pointer swapping
Compiler support for live updates and optimal switchover point

Persistence of state
Keeping static and global variable addresses consistent between firmware versions

Updates involve
Branching to the new firmware entrypoint
Execute the live update initialisation routine
Arrives in mew main and performs initialisation
This is when interrupts are temporally disabled

Hardware
Multi-Bank Non Volatile Memory
Interrupt Vector table swap
Ram block swap
Hardware LFU flag

\subsection{Dynamic Software Updates for Real-Time Systems}
\autocite{wahlerDynamicSoftwareUpdates2009} defines a solution for updating component-based cyclic embedded systems, without violating real-time constraints. 

\subsubsection*{Implementation}
This implementation focused on using COTS operating systems.

They used a custom component-based framework infrastructure on top of the operating system to execute software components, effectively an embedded middleware. Each component had its own address space with script separation and defined inputs and outputs. These components communicated using using message passing (channel buffers). A manager program (which was also an upgradable component) created and maintained the channels.

\begin{figure}[ht]
    \centering
    \includegraphics[width=8cm]{wahlerDynamicSoftwareUpdates2009_Function}
    \caption[Updating component 'History' \autocite{wahlerDynamicSoftwareUpdates2009}]
    {Updating component 'History' \autocite{wahlerDynamicSoftwareUpdates2009}}
    \label{fig:wahlerDynamicSoftwareUpdates2009_Function}
\end{figure}

How to identify points in time when an update can occur
System performs the checks at the end of every execution cycle

New update is sent to the target machine using OS functionality in a low priority thread
Upload is detected by the component manager
Tells the old component 
Hands the connections to channels back to the component manager and terminates
Component prime acquires the connects to the channels and begins operations

Steps 1 and 2 are not required to meet and deadlines, steps 3 to 5 must execute before the end of the cycle/

How to transfer the state of a component to a new version
State must be transferred in the same cycle of the handover
Data types may need to be converted (celsius to kelvin)

Component manager creates an area of shared memory that is passed to components.
Before a component terminates it writes its state to the area and adds version information.
When a component starts it reads the memory, asses if a state transformation must occur (these are stored within the components)

\subsection{Disruption-free Software Updates in Automation Systems}
Another approach to updating software at runtime without disruption was developed by \autocite{wahlerDisruptionfreeSoftwareUpdates2014}. This uses a component based architecture developed by ABB Corporate Research (FASA), shown in \autoref{fig:wahlerDisruptionfreeSoftwareUpdates2014_FASA}.

\subsubsection*{Implementation}
FASA defines function blocks that can be aggregated together to form a component, only compute components are stateful. These function blocks are executed cyclically at a desired frequency and connected by communication channels. A background thread with low priority performs the management actions. Multiple FASA systems are synchronised over the network using precision time protocol (PTP.)

\begin{figure}[ht]
    \centering
    \includegraphics[width=8cm]{wahlerDisruptionfreeSoftwareUpdates2014_FASA}
    \caption[FASA system architecture \autocite{wahlerDisruptionfreeSoftwareUpdates2014}]
    {FASA system architecture \autocite{wahlerDisruptionfreeSoftwareUpdates2014}}
    \label{fig:wahlerDisruptionfreeSoftwareUpdates2014_FASA}
\end{figure}

First the component binaries are loaded using shared libraries (DLLs), it is assumed the components are already present in the system. Next, the system is configured using configurations that define the layout of the components and channels. State is transferred between components using Teach and Learn blocks, optional type conversions occurs in these Learn blocks. Once all the controllers in the FASA network are ready to transfer to the new configuration, the switch command is issued.

\subsubsection*{Test Case}
Validated the solution with a test case, magnetic levitation experiment, instable physical process
Control algorithm of a magnetic levitation device at 1kHz

Most through implementation
Cyclic application execution
State transfer mechanisms
