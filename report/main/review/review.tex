Dynamic software updating (DSU) refers to software applications which can be updated while running and without interrupting operation. \autocite{hicksDynamicSoftwareUpdating2005}

Regular firmware upgrades require systems to be taken offline for firmware change and restart, which is generally time consuming and breaks continuity. High-availability systems typically use hardware redundancy to provide operational continuity throughout updates. This is at the cost of extra hardware and complexity. \autocite{raoLiveSeamlessFirmware2023}

Physical tasks performed by software are often expensive to interrupt with high down time costs. For example within power substations, a power outage for customers would be costly. Hence, software is hardly updated during an embedded system's lifetime (typically of over 30 years). There are several solutions to updating software dynamically; few of these have been adapted to real-time systems. \autocite{wahlerDynamicSoftwareUpdates2009}

This chapter evaluates the requirements for a system with dynamic software updates and the challenges involved. In addition, four existing implementations of dynamic updates for real-time systems are evaluated, considering both the advantages and disadvantages of each solution.

\subsection{Requirements for dynamic updates}
A dynamic software system can be summarised into several requirements, regardless of the implementation. Almost every DSU approach balances between the following requirements as they are contrary to each other. \autocite{mlinaricChallengesDynamicSoftware2020}

\begin{description}
    \item [Availability/Correctness] - Performing the software update should not impact the system's availability.
    \item [Flexibility] - Any part of a running system should be updatable without downtime. This includes low level-drivers and application software.
    \item [Low Overhead]- The additional infrastructure required to support software updates should impact performance as little as possible.
    \item [Simplicity] - The dynamic update system should be simple, both to reduce complexity of a system and to ease developer usage.
\end{description}

\subsubsection{Level of Update}
A software update often can consist of very minor changes, possibly fixing a software bug with a single line of code. Level of update considers how much of the software is updated, whether that is components or entire system \autocite{seifzadehSurveyDynamicSoftware2013}.

\subsubsection{Dependent Components}
The communications between software modules (functions or collections of functions) are often not singular. Instead a program may contain many communication between many functions in a many-to-many relationship. 

This increases the complexity of upgrading singular modules, as one change could affect all other modules. Sometimes the data types used in communications also changes, so multiple dependant modules may need upgrading to use the new types.
