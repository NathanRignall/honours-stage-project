\subsection{Real-Time}
A real-time system is defined as a system which requires correct logical operation with completion in a configured deadline. This is in contrast to a non-real-time system which correct operation is desired but lacks configured deadlines. \autocite{kaviRealTimeSystems2009}

These real-time systems can be categorised into hard and soft. Hard real-time systems contain strict timing constraints, where a response must be calculated in a specified time-frame and a missed deadline could result in a catastrophic outcome. Soft real-time systems also have timing constraints, but a missed deadline should not result in a catastrophic outcome.

Typical hard real-time systems include aircraft or robotic control computers and soft real-time systems include media players or gaming computers. Soft real-time systems can be used in control applications, but the soft timing must be considered in the system design.

\subsection{Control Systems}
A control system is a system that is designed to manage, regulate and stabilize the behaviour of a dynamic system. Often computers are used to implement real-time control laws in applications such as aircraft fight control or chemical process controls.

\subsection{Virtualization}
% intro
Virtual machines create isolated and/or emulated computing environments by abstracting resources within a physical machine \autocite{liSurveyVirtualMachine2010}. Software known as hypervisors can provide this abstraction layer \autocite{rountreeSystemSecurity2011}.

% type 1
Hypervisors that directly access the underlying machine resources are known as Type 1 \textit{bare metal} hypervisors, examples include Hyper-V \autocite{phsteeHyperVArchitecture2023}, Xen \autocite{xenprojectVirtualization}, ESXi \autocite{vmwareWhatESXI} or KVM \autocite{redhatWhatKVM}.

\begin{figure}[ht]
    \centering

    \caption[Type 1 hypervisor architecture \autocite{awsWhatDifferenceType}]
    {Type 1 hypervisor architecture \autocite{awsWhatDifferenceType}}
    \label{fig:awsWhatDifferenceType}
\end{figure}

% type 2
Rather type 2 hypervisors negotiate resource allocation with the operating system, which makes the process slower and less efficient, \autocite{awsWhatDifferenceType} such as VMware Workstation \autocite{vmwareWhatHypervisorVMware}.

% types
A fully virtualized hypervisor emulates privileged instructions and I/O operations, abstracting the hardware resources from the virtual machine. The guest operating system therefore requires no modifications as it is unaware of the virtualisation. In contrast, with para-virtualization the guest operating system requires significant modifications and is aware of the underlying hardware. Hardware assisted virtualisation uses additional CPU instructions to isolate virtual machines in a hypervisor, for example AMD-V \autocite{liSurveyVirtualMachine2010}.

% why
Hypervisors, particularly type 1, are a useful tool for isolating software components on a single piece of hardware. 

\subsection{Mixed Criticality}
Mixed criticality refers to heterogeneous software with mixed software integrities running on a shared hardware platform. Virtualisation technology is often used to isolate this software, even in a real-time environment. \autocite{guStateoftheArtSurveyRealTime2012}.

The ARINC 653 standard is a software standard that defines a software architecture for both spatial and temporal partitioning of virtual machines or \textit{partitions}. Spatial refers to the isolation of code and data between virtual machines while temporal aims to limit the impacts of resource consumptions across virtual machines \autocite{cinqueVirtualizingMixedcriticalitySystems2022}. Hypervisors that follow this standard or similar must be certified when used in a safety critical application.

\subsection{Embedded Middleware}
% intro
There is no one definition for middleware used in embedded systems. It is usually considered the piece of software that resides between the operating system and application software. Software that sits between application software can also be classed as middleware. \autocite{gazisMiddleware101What2022}

\subsection{Integrated Modular Avionics (IMA)}
Avionics are a category of electronic systems that are specifically design for use in aircraft. 
There are several architectures that are used in avionics. Middleware solutions are often used in this scenario for the benefits of software portability. \autocite{darweshDemonstratorVerificationSelective2018}

Aircraft systems have gradually evolved away from a federated architecture into a more modular system. A federated architecture usually consists of multiple independent components with self-allocation and self-management. An integrated modular avionics (IMA) architecture brings the independent components into a single physical region, with resource sharing. A distributed integrated modular avionics (DIMA) architecture separates into multiple physical regions with distributed management for redundancy. \autocite{debarrosDistributedIntegratedModular2019}
